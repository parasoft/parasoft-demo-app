# Spec: PDA-1546

## Source

- Retrieved: 2026-10-10
- Title: Add option to immediately put order into PROCESSED state

### Current Jira Description

As a Parasoft employee who is using the demo app to showcase the ability to use AI to create SOAtest test scenarios, I can run a scenario to place an order that has an assertion on the state of the order and consistently get a passing result.

When I use SOAtest MCP with an LLM client like Copilot to create a test scenario that adds two items to the cart, submits the order, and then verifies that the order has been placed, I will get a test scenario like the one attached to this issue. The test scenario calls the following APIs:

1. `POST /cartItems`
2. `POST /cartItems`
3. `POST /orders`
4. `GET /orders/{orderNumber}`

It creates assertions on the 4th test, and usually one of the assertions is that the state==SUBMITTED. However, the state can be either SUBMITTED or PROCESSED, depending on how quickly things work on the backend. When an order is placed, the state is initially SUBMITTED. There is a callback handler in ItemInventoryService that checks the inventory and then sets the status to PROCESSED or CANCELED. But the workflow is asynchronous so the result is not guaranteed.

We would like to add an option to the Settings page that allows a user to choose between the current behavior and a new behavior where the order is immediately put into PROCESSED state. It may still get set to CANCELED if there is not enough inventory - but if there is enough inventory, it should get set to PROCESSED initially and never change.

### Subsequent Jira Decision

Alfie Wang, 2026-10-08T19:39:54.000-0700:

> After some discussion with Roller and Yuqian, we decided to go with the simpler implementation, i.e. add an item in a new *Additional Settings* section (between *DEMO BUGS* and *INDUSTRY SITE DESIGN*) to enable or disable (default) setting the order to **PROCESSED** state instead of **SUBMITTED** state when it is placed. In this implementation, the order may get changed to **CANCELED** state later if there is not enough inventory.

## Goal

Allow users to enable immediate `PROCESSED` status for newly placed orders so SOAtest scenarios can consistently assert that status when inventory is sufficient.

## In Scope

- Add an enable/disable option to a new Additional Settings section between Demo Bugs and Industry Site Design.
- Create orders with `PROCESSED` status when the option is enabled.
- Retain initial `SUBMITTED` status when the option is disabled.
- Continue asynchronous inventory processing and cancellation when stock is insufficient.
- Integrate the option with the existing preferences, translations, and shared order service (inferred).
- Handle successful inventory confirmation for an already processed order and retain existing notifications (inferred).
- Add automated regression coverage and user documentation (inferred).

## Out of Scope

Not explicitly defined in Jira.

## Behavior

- Users can enable or disable immediate processing through Demo Administration > Additional Settings, between Demo Bugs and Industry Site Design.
- When enabled, an order is initially saved and returned as `PROCESSED`.
- When disabled, an order is initially `SUBMITTED` and the existing inventory workflow determines its later status.
- With sufficient inventory, an order created as `PROCESSED` stays `PROCESSED` when inventory processing succeeds.
- With insufficient inventory, an order created as `PROCESSED` may later become `CANCELED`.
- The option affects new orders; changing it does not rewrite existing orders (inferred).
- The shared creation flow applies the option for existing clients and skins (inferred).
- The option uses the existing preferences save, reload, and restart behavior and starts disabled. Resetting industry databases preserves global preferences, including this option (inferred).

## Edge Cases (Optional)

- A status assertion may observe `CANCELED` if inventory is insufficient.
- A successful inventory response for an already `PROCESSED` order is a confirmation, not an invalid transition (inferred).
- Later valid purchaser or approver transitions continue to work (inferred).

## Implementation

- A standalone Boolean `newOrdersInitiallyProcessed` global preference is stored in its own database column and exposed independently of `demoBugs`. It defaults to false; absent or null request values mean false.
- The entity and preferences response DTO omit the new field when false or null, and emit `newOrdersInitiallyProcessed: true` when enabled. Other response fields retain their existing serialization.
- Global table initialization adds the column to existing databases and migrates the earlier `PROCESS_ORDERS_IMMEDIATELY` demo-bug record into it before preferences are loaded. Unrelated demo-bug records are retained.
- `demoAdmin.html` places the checkbox in Additional Settings between Demo Bugs and Industry Site Design. `demoAdmin.js` reloads the saved value, and all six existing translation bundles provide the section heading and checkbox label.
- `OrderService.addNewOrder` selects `PROCESSED` or `SUBMITTED` before both order saves, while retaining cart clearing and inventory requests.
- The order service resolves the global preferences service lazily to avoid the inventory response listener/global preferences startup dependency cycle. A code comment explains this handling.
- Inventory success recognizes an existing `PROCESSED` state and sends the normal approver notification without attempting a same-state update or changing existing comments.
- Inventory failure explicitly permits `PROCESSED` to `CANCELED`, because those statuses share the same priority. All other status guards remain in place.
- Regression tests cover enabled/disabled creation, persisted preference reload and disabling, successful confirmation, failure cancellation, and the saved-checkbox binding, absent request values, default response compatibility, and migration of previously saved settings.
